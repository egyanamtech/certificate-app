Thought / Rationale

The application deliberately has no single fixed web domain: it binds on 0.0.0.0:5000 and is reached over the LAN by IP (10.19.172.47 / 192.168.29.85) or via same-origin on whatever host serves it. That keeps the API surface behind one origin and avoids CORS exposure, and lets a university run it on intranet hosts before attaching a public DNS name.

All third-party traffic is explicit and narrow: certificate blobs go to Pinata/IPFS, hash anchors to the Sepolia RPC, and one-time passwords to a single configured SMS domain. Student personal data never leaves the local PostgreSQL instance; the public verify endpoint returns only a validity flag plus the CID.

For a production rollout the recommendation is to front the server with a real domain and TLS (e.g. portal.<university>.edu → reverse proxy → :5000), keep the DB and SMS gateway on the private network, and rotate the Pinata/Sepolia credentials. Until then, the IP-based hosts above are the authoritative “domains” in use.

1. Admin Authentication Flow

Admin UI ──POST /api/admin/login──▶ Express
   │ body: { username, password }
   ├─▶ loginAttempts (in-memory Map, IP key) ── 429 if rate limit hit
   ├─▶ SELECT * FROM users WHERE username = ?
   ├─▶ verifyPass(): old sha256 OR scrypt (auto-migrate to scrypt on success)
   ├─▶ createSession() → INSERT app_sessions → token
   ├─▶ INSERT activity (ADMIN_LOGIN) + monitor_events (info)
   └─▶ 200 { token, role, permissions[], departments[] } ──▶ localStorage admin_token / admin_user

Every protected call: fetch('/api/...') + headers   x-admin-user   x-auth-token
   requireAdmin ── isAdminRequest() ──▶ DB session lookup ──▶ 200 | 403 "Admin access required"
   requirePerm('dpia'|'results'|'issues'|'monitor') ──▶ role admin OR permissions[] contains perm

14. Failure & Safety Properties

Schema idempotency: CREATE TABLE IF NOT EXISTS + ALTER TABLE ADD COLUMN IF NOT EXISTS + guards make restarts safe.
DPIA FK cascade: deleting a DPIA removes its risks and audit rows via ON DELETE CASCADE.
Login throttling: in-memory per-IP attempt window → 429 lockout (15 min); OTP stored hashed (sha256) with 5-min TTL and attempt cap.
Route-order rule: static DPIA subroutes (report, workflow, dashboard) are registered before /api/dpia/:id.
RBAC: roles (admin, dept-head, privacy-manager, cybersecurity, hr, legal) + per-permission gates on DPIA/results/issues/monitor.
Agent security: monitor events require x-monitor-token and a registered, enabled app_key.
